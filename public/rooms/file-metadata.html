File metadata: what a photo tells you besides the picture

Every image file can carry information you never see on screen: who took it, what software made it, sometimes even where it was taken. This room uses two real image files with genuine embedded metadata, read entirely in your browser.

Introduction

A photo file usually contains more than pixels. Alongside the image data, many formats carry a block of metadata: text fields describing the file itself. Real cameras and phones commonly use a standard called EXIF, which can include the camera model, the software used, the date, and sometimes GPS coordinates. The two images in this room use a simpler, equivalent format (PNG text chunks) so the same idea can be read in plain JavaScript, with no external library.

Why does it matter?

People regularly share photos without realising what travels with them. A holiday photo posted the moment it’s taken can reveal exact GPS coordinates of someone’s home. A screenshot might carry the name of the software, account, or device that made it. None of this is visible by just looking at the picture.

Where does this happen in real life?

Metadata has been used to locate people who believed they had hidden their location, to attribute anonymous leaks to a specific device or author, and in several well-documented cases, to undermine an attempt at anonymity entirely by accident.

An analogy

Metadata is like the postmark and sender’s return address on an envelope: the letter inside might say nothing identifying at all, but the envelope itself already told you who sent it, from where, and when.

A note on these images

Both images here are simple generated graphics, not real photos, with fictional metadata added for teaching purposes. The technique you practise — reading embedded text metadata — applies the same way to a real photo’s real EXIF data.

Learning objectives

  • Explain what image metadata is and how it differs from the visible picture.
  • Read a file’s embedded text fields using a browser-based tool.

Theory

Idea 1: two layers in one file

An image file typically has the actual picture data, and separately, a block of metadata: short text fields describing the file. You never see the metadata by just viewing the image; it only appears if something specifically reads it.

Image file
 ├─ Picture data        (what you see when you open it)
 └─ Metadata fields     (invisible unless something reads them)
      ├─ Software: "..."
      ├─ Author: "..."
      └─ sometimes: GPS location, device model, timestamp

Idea 2: what real cameras and phones add

The EXIF standard, used by most cameras and phone cameras, can include the device make and model, the exact date and time, camera settings, and, if location services were enabled, precise GPS coordinates accurate to a few metres. None of it requires the photographer to type anything in: the device adds it automatically.

Mini quiz: what’s in the metadata?

A photo taken on a phone with location services enabled is shared online exactly as captured, with no editing. What might its metadata reveal that isn’t visible in the picture itself?

Idea 3: reading it yourself

You don’t need special software to check: many operating systems show basic file properties on right-click, and dedicated tools (or, for this room, a small in-browser reader) can show every embedded field. It is worth checking before sharing anything you didn’t create yourself, or anything you took somewhere you’d rather not reveal.

Idea 4: the fix is to strip it before sharing

Most devices and many sharing platforms offer a "remove location data" or similar option before upload. Stripping metadata deletes these hidden fields entirely, leaving only the picture itself; it is a simple step that removes the whole category of risk.

Demonstration

Worked example. A fictional company social media intern shares a product photo straight from their phone. Reading the file’s metadata afterwards shows:

Software: ClydeCapture Mobile v3.2
Author: marketing-temp
Timestamp: 2026-04-02 16:47

Nothing here looks dangerous at a glance. But it already reveals the exact app and account used, and the precise time the photo was taken, none of which was mentioned in the post itself. A photo taken with GPS enabled could just as easily have included exact coordinates. The fix each time is the same: check before posting, and strip location and unnecessary fields where the option exists.

Reflection questions

Discussion points

Open-ended: most learners note that the Location field is the most concerning, since it gives a precise, real-world detail with no visual indication it was ever recorded.

Discussion points

It could reveal the exact location of an office, a loading bay, or other security-relevant site detail, or build up a pattern of staff movements over time, none of which the company intended to disclose.

Discussion points

Encoding only disguises data; it provides no real protection, as you learned in Path 2. Hiding something inside a metadata field as Base64 does not make it secret, only slightly less obvious at a glance.

Discussion points

It confirms the fields are genuinely removed from the file, not merely hidden from view. Anyone who later reads the stripped file’s metadata, with any tool, would also find nothing.

Discussion points

Examples: posting a photo taken at home before selling something online, sharing a screenshot that might include device or account details, posting travel photos in real time rather than after leaving a location.

Key takeaways

  • Image files can carry metadata, invisible fields describing the file, separate from the picture itself.
  • Real cameras and phones often embed GPS location automatically when enabled, with no extra action from the user.
  • A field can look like harmless text and still be encoded, which is not the same as being protected.
  • Stripping metadata removes these hidden fields entirely, which is why it is a recommended step before sharing.
  • Checking a file’s metadata takes seconds and reveals exactly what it reveals: nothing more, nothing less.
