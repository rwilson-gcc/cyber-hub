Encoding: Base64, hex and friends

Data is often disguised so it can travel safely, not so it stays secret. This room teaches you to recognise the common encodings on sight, reverse them, and see why encoding is not encryption. Every message here is fictional.

Introduction

Computers move data through systems that only understand certain characters. Encoding is the process of rewriting data in a different form so it fits: Base64 turns anything into plain letters and digits, hex writes each byte as two characters, and URL encoding makes text safe to put in a web address.

Why does it matter?

Encoded data looks scrambled, which makes people think it is protected. It is not. There is no key and no secret, so anyone who recognises the format can reverse it in seconds. Credentials, tokens and personal data are regularly exposed because someone treated encoding as security.

Where does this happen in real life?

Web logins using HTTP Basic authentication send username:password as Base64. Cookies, email attachments and JSON Web Tokens use it too, and malware authors often wrap their code in layers of encoding to look harmless.

An analogy

Writing a message in Morse code doesn’t hide it from anyone who knows Morse. It just changes the alphabet. Encoding is the same: a different way of writing the same thing that anyone with the chart can read back.

Stay legal

Only decode data you are entitled to see. Capturing other people’s traffic or credentials without permission is a criminal offence under the Computer Misuse Act 1990. Every message in this room is fictional and generated in your browser.

Learning objectives

  • Explain what encoding is and how it differs from encryption.
  • Recognise Base64, hex and URL encoding from how they look.
  • Decode each one by hand or with a tool, one layer at a time.
  • Spot layered encoding and know when to stop (when the result is readable).
  • Explain why encoded credentials are not protected credentials.

Theory

Idea 1: encoding is just a different way of writing

The same text can be written in several forms. None of them uses a key, and each can be turned back into the original by anyone who knows the rules.

Text      Hi
Hex       48 69
Base64    SGk=
URL       Hi   (no change: nothing needs escaping)
  1. 1. OriginalReadable text or data.
  2. 2. EncodeRewritten using a fixed, public rule.
  3. 3. TravelPasses safely through systems with limits.
  4. 4. DecodeAnyone can reverse it. No key needed.

Idea 2: recognising the common encodings

Base64

Letters, digits, + and /, often ending in = padding. Length is a multiple of 4. Example: SGVsbG8=

Hex

Only 0-9 and a-f, in an even-length run, sometimes spaced into pairs. Example: 48 65 6c 6c 6f

URL encoding

Normal text with % followed by two hex digits where a character needed escaping. %20 is a space.

Mini quiz: what is it?

A captured string uses only the characters 0-9 and a-f, and its length is even. Which encoding is it most likely to be?

Idea 3: layers

Data is sometimes encoded more than once, for example hex first and then Base64. Decode one layer at a time and look at the result. If it is still unreadable, work out what it looks like now and decode again. When you can read it, you are done.

Idea 4: encoding is not encryption

Encryption needs a secret key: without it the data stays unreadable. Encoding needs nothing, so it offers no protection at all. HTTP Basic authentication is the classic example: the password is only Base64, so the connection must use HTTPS to protect it.

Mini quiz: is it secure?

A developer stores customer passwords as Base64 text "so they can’t be read". Is that secure?

Demonstration

Worked example on a fictional site, fernhill-bakery.example. A tester reviewing a web request spots this header:

Authorization: Basic YmFrZXI6b3ZlbjEyMw==

The trailing == and the mix of letters and digits suggest Base64. Decoding it gives:

baker:oven123

A username and password, readable in one step and with no tools beyond a decoder. If that request had gone over plain HTTP, anyone on the network could have read it. The fix is not a cleverer encoding: it is HTTPS, and ideally a login system that doesn’t send the password on every request.

Reflection questions

  

    
Discussion points
Item A: mixed letters and digits with = padding (Base64). Item B: only 0-9 and a-f in pairs (hex). Item C: % followed by two hex digits (URL encoding). Recognition comes from the character set, the length pattern and any padding.

  

    
Discussion points
There is no key or secret. The rules are public, so anyone can reverse it. Encryption relies on a key that an attacker doesn’t have.

  

    
Discussion points
Examples: Base64 lets binary data (images, attachments) travel through text-only systems such as email or JSON; URL encoding stops special characters breaking a web address. Encoding is about compatibility, not secrecy.

  

    
Discussion points
Layers can slip past simple filters or make a payload look harmless at a glance, but they add no security: each layer is trivially reversible, and the real content is still exposed once decoded.

  

    
Discussion points
HTTP Basic auth headers, cookies and tokens such as JWTs. Proper protection is HTTPS in transit, and on the server, passwords stored with a salted, slow hash rather than encoded or reversibly encrypted.

Key takeaways

  
    
    
  • Encoding changes how data is written, not who can read it.
    • 
    
  • Base64, hex and URL encoding each have a recognisable look.
    • 
    
  • Decode one layer at a time and stop when the result is readable.
    • 
    
  • Anything protected only by encoding should be treated as plain text.
    • 
    
  • Real protection needs encryption with a key, hashing for passwords, and HTTPS in transit.
