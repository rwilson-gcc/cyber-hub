Access control: who's allowed to see what

Logging in answers "who are you?" Access control answers the much more important question: "what should you be allowed to do, now that we know?" This room is about what happens when that second question never gets asked.

Introduction

Authentication checks who you are, usually with a username and password. Access control is a separate, later check: now that we know who you are, what are you actually allowed to see or do? A huge number of real vulnerabilities come from sites that nail the first check and completely forget the second.

Why does it matter?

If access control is missing or incomplete, logging in as anyone, even a brand-new free account, can be enough to reach data or pages that should be locked away. No password cracking required, just a bit of curiosity about URLs and IDs.

Where does this happen in real life?

Broken access control is consistently one of the most reported categories of real-world web vulnerabilities, because it's so easy to introduce (one missing check) and so easy to find (just change a number) once you know to look.

An analogy

Picture a block of storage units. Everyone gets a key that opens their own unit. Access control failures are like discovering that key also opens unit 47, two doors down, which happens to belong to someone else — or that the "Staff Only" door at the end of the corridor was never actually locked at all.

Stay legal

Only test access control on systems you own or have permission to test. Viewing someone else's real data without authorisation is a criminal offence, even if the flaw was trivial to find. This room is a complete simulation.

Learning objectives

  • Explain the difference between authentication and access control.
  • Define horizontal and vertical privilege escalation, and tell them apart.

Theory

Idea 1: two directions of privilege escalation

Horizontal

Same level of access, but reaching someone else's data. A regular user viewing another regular user's private records.

Vertical

Climbing up a level. A regular user reaching admin-only pages or actions.

Mini quiz: horizontal or vertical?

A logged-in customer changes an order number in the URL and sees a stranger's order. Which type of privilege escalation is this?

Idea 2: IDOR, insecure direct object reference

Many pages use an ID straight from the URL to decide what to show you, like /invoices/1189. That's fine, as long as the server also checks the invoice actually belongs to you. An IDOR happens when that ownership check is missing, so simply changing the number shows someone else's data.

GET /invoices/1189   → your invoice, fine
GET /invoices/1188   → should be blocked, but isn't

Idea 3: a hidden link is not a locked door

Developers often hide admin links from regular users in the page's design. That's a usability choice, not a security control. If the server doesn't separately check the user's role before showing the admin page, typing the URL directly, known as forced browsing, gets you straight in. This is sometimes called a missing function-level access control.

  1. 1. Hide the linkFine for tidiness, but not a defence on its own.
  2. 2. User requests pageBy clicking, or by typing the URL directly.
  3. 3. Server must checkIs this user actually allowed to see this page?
  4. 4. Allow or refuseThe check has to happen here, every time, no exceptions.

Demonstration

Worked example on a fictional site, brightpath-learning.example, an online course platform:

Logged in as a student, visiting /invoices/1190 shows your own invoice. Out of curiosity, you try /invoices/1189:

GET /invoices/1189  → 200 OK
Name: J. Okafor
Course: Advanced Spreadsheets
Amount paid: £129.00

That's someone else's invoice, shown with no ownership check at all. This is horizontal privilege escalation via an IDOR.

Separately, the student notices a link that isn't shown in their menu, but has seen mentioned in a staff training doc: /admin/reports. They try it directly:

GET /admin/reports  → 200 OK
(Full list of every course's enrolment and revenue figures)

No login as staff was needed, just the URL. That's vertical privilege escalation, and specifically a missing function-level access control. The fix for both: check, on the server, that the logged-in user actually owns the resource or holds the right role, every single time, not just in the menu design.

Reflection questions

Discussion points

Hiding a link only stops casual browsing through the interface. Anyone who guesses, remembers or is told the URL can still request the page directly, so the real check has to happen on the server.

Discussion points

The barrier to entry is tiny: anyone with any account, even a free one, can try changing IDs. No special access or technical skill is needed, which is exactly why it's found so often.

Discussion points

Always check, server-side, that the logged-in user owns the specific record they're asking for, and holds the specific role a page requires, on every single request.

Discussion points

Both rely on a page existing and being reachable with the right path, even though nothing on the site pointed a normal visitor towards it. Obscurity isn't protection in either case.

Discussion points

Horizontal: a user can see someone else's stuff at the same level as them. Vertical: a user can reach pages meant for a higher level of access than they actually have.

Key takeaways

  • Authentication checks who you are; access control checks what you're allowed to do. Both are needed.
  • Horizontal escalation reaches another user's data at the same level; vertical escalation reaches a higher level entirely.
  • An IDOR is usually just a missing ownership check behind an ID in a URL.
  • Hiding a link from the menu is a design choice, not a security boundary.
  • Every access decision needs to be enforced on the server, on every request.
