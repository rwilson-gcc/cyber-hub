XOR, JWTs and hashes

Encoding hides nothing, ciphers hide data behind a key, hashes are one-way, and signatures prove nothing was changed. This room helps you tell them apart. Every token and message here is fictional.

Introduction

Security is full of terms that sound similar but do different jobs. XOR is a simple operation that combines data with a key. A JSON Web Token (JWT) is a compact way of proving who you are to a website. A hash is a one-way fingerprint of some data. This room covers all three and shows what each one can and can’t do.

Why does it matter?

Mixing these up causes real mistakes: believing a token’s contents are private when they are only encoded, thinking a short XOR key is encryption, or storing passwords with a hash that is trivial to look up. Knowing which tool offers which guarantee is a core skill.

Where does this happen in real life?

JWTs carry your identity on many modern sites and APIs. Hashes are used to store passwords and to check files haven’t changed. XOR is a building block inside real ciphers, and also a favourite for weak home-made schemes in malware.

An analogy

A hash is like a fingerprint: it identifies a person but you can’t rebuild the person from it. A signature on a letter proves who wrote it and that nobody edited it, but anyone can still read the letter. Encryption is the sealed envelope.

Stay legal

Only inspect tokens, hashes and data you are entitled to look at. Tampering with other people’s tokens or cracking passwords you don’t own is an offence under the Computer Misuse Act 1990. Everything in this room is fictional and generated in your browser.

Theory

Idea 1: XOR with a key

XOR compares two bits and gives 1 when they differ. Applying it between your data and a key scrambles the data, and applying the same key again restores it:

data  XOR  key  =  scrambled
scrambled  XOR  key  =  data     (same key undoes it)

If the key is a single byte there are only 256 possibilities, so an attacker can try them all and look for readable text. XOR is only strong when the key is as long as the message, random and never reused, which is rarely true in home-made schemes.

Idea 2: JSON Web Tokens

A JWT has three parts joined by dots: a header, a payload and a signature. The header and payload are just JSON written in Base64URL, so anyone holding the token can read them. The signature is made using a secret that only the server knows, so if someone changes the payload the signature no longer matches and the server should reject the token.

header.payload.signature
Header

Says how the token is signed, for example HS256.

Payload

The claims: who the user is, their role, when it expires. Readable by anyone.

Signature

Proves the token wasn’t changed. It does not hide anything.

Idea 3: hashes

A hash function turns any input into a fixed-length fingerprint. The same input always gives the same hash, a tiny change gives a completely different one, and you can’t turn a hash back into the input. You can often recognise the type from its length in hex characters:

HashLength in hex characters
MD532
SHA-140
SHA-25664

MD5 and SHA-1 are old and fast, which is bad for passwords because attackers can try billions of guesses a second against stolen hashes. Passwords need a slow, salted hash such as bcrypt or Argon2.

Idea 4: four tools, four jobs

ToolNeeds a key?Reversible?Job
EncodingNoYes, by anyoneCompatibility
EncryptionYesYes, with the keyConfidentiality
HashingNoNoFingerprints, password storage
SigningYesNot applicableIntegrity and authenticity

Demonstration

Worked example on a fictional site, glenfield-tickets.example. After logging in, a tester finds this token in a cookie:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhbXkiLCJyb2xlIjoic3R1ZGVudCJ9.…signature…

Splitting on the dots and decoding the first two parts as Base64URL gives readable JSON:

{"alg":"HS256","typ":"JWT"}
{"sub":"amy","role":"student"}

The tester can read everything about the session without any secret. They then try changing "role":"student" to "admin". A correctly built server recalculates the signature, sees it no longer matches, and rejects the token. A server that forgets to check the signature would accept it, which is a real and serious class of bug.

Reflection questions

  

    
Discussion points
The payload shows the user, role and other claims in plain JSON. Anyone who intercepts the token learns that, so sensitive data should never be put in a JWT payload.

  

    
Discussion points
It protects integrity: any change to the header or payload makes the signature fail. It does not provide confidentiality, since the payload is still readable.

  

    
Discussion points
They are fast, so attackers can test enormous numbers of guesses per second, and unsalted hashes can be looked up in precomputed tables. Passwords need slow, salted hashing such as bcrypt, scrypt or Argon2.

  

    
Discussion points
Only 256 keys exist, and the result is obviously readable when correct. XOR is only secure as a one-time pad: a truly random key as long as the message and never reused.

  

    
Discussion points
Encoding: Base64 for attachments. Encryption: AES for files or HTTPS traffic. Hashing: bcrypt for stored passwords. Signing: a JWT signature or a software update signature.

Key takeaways

  
    
    
  • XOR is reversible with the same key, and a single-byte key is trivial to brute force.
    • 
    
  • A JWT is signed, not hidden: anyone can read its payload.
    • 
    
  • A signature protects integrity, not confidentiality.
    • 
    
  • Hash type can often be recognised from length, but fast hashes are poor for passwords.
