Upload and logic flaws: when the rules have gaps

Some weaknesses aren’t about breaking an input filter, they are about a feature that trusted the wrong thing, or a workflow that assumed everyone follows the steps in order. This room covers two of the most common: unsafe uploads, and business logic that bends further than it should.

Introduction

Not every flaw involves injecting code. A file upload feature can be unsafe simply by trusting the wrong signal about what a file is. A shop’s basket can be broken by a number that was never range-checked. A multi-step process can be skipped if only the page, not the server, enforces the order. These are called logic flaws: the code runs exactly as written, but the rules it enforces have a gap.

Why does it matter?

Automated scanners are good at finding injection but often miss logic flaws entirely, because nothing about them looks malformed: every request is syntactically valid. Finding these needs you to understand what the feature was supposed to guarantee, and check whether it actually does.

Where does this happen in real life?

Profile picture and document upload features, shopping basket and coupon systems, and multi-step checkouts or sign-up flows are classic places both kinds of flaw turn up, often in otherwise well-built sites.

An analogy

A bouncer who only checks the label sewn into a jacket, not what’s actually inside the venue bag, can be fooled by anyone who simply changes the label. A till that lets you "return" more items than you bought, crediting money back, isn’t broken code: it’s a rule nobody thought to write.

Stay legal

Only test systems you own or have explicit permission to test. Exploiting upload or logic flaws on a real site without authorisation is a criminal offence under the Computer Misuse Act 1990. The simulated upload checker in this room only evaluates filename and declared type strings: no file is ever actually uploaded, stored or run.

Theory

Idea 1: a file is not what its name or label claims

A file’s extension (.jpg) and its declared content type (the Content-Type header the browser sends) are both just labels the uploader chose. Neither is checked against the file’s actual content by a naive upload handler, so both can be set to anything.

photo.jpg.php     ← some servers run the file based on the LAST part, ignoring the rest
shell.php%00.jpg  ← older systems could be tricked by a null byte before the real extension
Content-Type: image/jpeg   ← sent by the browser, not verified against the file itself

Idea 2: business logic flaws

A logic flaw is a gap in the rules, not the syntax. Every request involved is well-formed, so there is nothing for an injection filter to catch. Common examples: a quantity field that accepts negative numbers, discount codes that can be applied more than once, or a price recalculated client-side instead of looked up server-side.

quantity = -3
total = quantity * unit_price     ← produces a negative total: a "refund" for buying nothing
Mini quiz: spotting a logic flaw

A basket lets you apply the same single-use coupon code three times by resubmitting the form. What kind of flaw is this?

Idea 3: workflows are only as strict as the server makes them

A multi-step process (verify email, then set a password, then finish sign-up) is often enforced only by which page the user is shown next. If the server doesn’t independently track which steps have genuinely been completed, a user can jump straight to the final step’s request and skip everything in between.

Idea 4: the fixes

FlawFix
Unsafe uploadCheck the file’s actual content (not just its name), use an allow-list of real types, store uploads outside the web root with generated names
Negative or illogical valuesRange-check every value server-side; recalculate totals server-side rather than trusting a client-sent total
Reused codes / stacked discountsTrack usage server-side and enforce limits there, not just in the page
Skipped workflow stepsTrack real progress server-side (a status flag per user) and check it before allowing the next step, not just which page was shown

Demonstration

Worked example on a fictional site, harbour-print-shop.example. Its upload form only checks the filename ends in an allowed-looking string:

if filename.endswith((".jpg", ".png", ".pdf")): accept()

A tester uploads a file named design.php.jpg. The check passes because the filename does end in .jpg. But depending on how the server is configured, it might store and later execute the file based on an earlier part of the name, or a misconfigured server might run any file with .php anywhere in the name. Separately, the same site’s basket accepts a quantity of -2 for an item, and the total goes negative, which the checkout happily treats as a discount on the rest of the order. Neither bug needed a single special character: both needed only a value the developer never imagined.

Reflection questions

Discussion points

The filename is just a label the uploader chose; it says nothing provable about the file’s real content. A naive check can be satisfied by a name engineered to end the right way while being something else entirely.

Discussion points

Range-checked it: rejected anything below a sensible minimum (such as 1) before it was ever used in the total calculation, rather than multiplying whatever value arrived.

Discussion points

The server checked that the code was valid but never recorded that this basket, or this account, had already used it. It would need to track coupon usage server-side and reject a second application of the same single-use code.

Discussion points

The order of steps was only enforced by which page the user happened to be shown, not by anything the server independently verified. The server needed its own record of which steps had genuinely been completed before allowing the next one.

Discussion points

"What is actually enforcing this rule, and is it enforced on the server, independent of what the client sends or which page it requests?" All three flaws trusted something client-controlled, whether that was a filename, a quantity, or simply which page was requested next.

Key takeaways

  • A file’s extension or declared type is a label the uploader controls, not proof of its content.
  • Logic flaws exploit missing rules, not malformed input, which is why scanners often miss them.
  • Every numeric value from the client needs a sensible range check on the server.
  • Single-use codes and limits must be tracked and enforced server-side.
  • A multi-step workflow needs the server, not just the page shown, to track genuine progress.
