Introduction

Finding a vulnerability is only half the job. This room reviews four short, fictional code snippets, each with the kind of flaw you’ve met in this path and in Path 1, and asks you to choose the fix that actually removes the cause rather than one that only looks safer.

Why does it matter?

Many real fixes make a vulnerability harder to trigger without closing it: a filter that blocks today’s known payload, an error message that’s merely harder to read. A developer who can tell a real fix from a cosmetic one writes code that stays secure as attackers keep trying new angles.

Where does this happen in real life?

Code review, whether by a colleague or an automated tool, is where these decisions get made every day. Getting it right here is practice for exactly that moment.

An analogy

Putting a sign on a broken step that says “mind the gap” is a cosmetic fix: it relies on everyone reading it, every time. Fixing the step is a real fix: it removes the hazard, not just the warning.

A note on the code

Every snippet in this room is short, fictional pseudo-code written for teaching. None of it is real production code, and nothing here runs: you are reviewing it, not executing it.

Learning objectives

  • Recognise the real fix for SQL injection, XSS, path traversal and command injection.
  • Tell a root-cause fix apart from one that only hides the symptom.
  • Explain why validating on the server, not just the client, matters even when client-side checks exist.
  • Apply more than one fix to a snippet that combines two flaws, in a sensible order.
  • Describe defence in depth as a backup to the real fix, not a replacement for it.

Theory

Idea 1: symptom fixes vs cause fixes

A symptom fix changes the attack that was tried without removing the underlying mistake. A cause fix removes the mistake, so the whole class of attack stops working, including variations nobody has tried yet.

FlawSymptom fix (weak)Cause fix (real)
SQL injectionBlock the word SELECTParameterised queries
XSSStrip the word <script>Context-aware output encoding
Path traversalStrip ../Resolve and check the final path stays inside the allowed folder
Command injectionStrip ; and &&Never build a shell string; call the function directly with arguments
Mini quiz: spot the symptom fix

A developer fixes a path traversal bug by replacing every ../ in the input with an empty string before using it. Is this a reliable fix?

Idea 2: validate on the server, always

Client-side checks (JavaScript, HTML maxlength, disabled buttons) are a convenience for honest users. They run entirely in the browser, which anyone can inspect and bypass by editing the request directly, as you did in earlier rooms. The server must repeat every check that matters, because the server is the only part of the system an attacker can’t directly control.

Mini quiz: where must validation happen?

A form uses JavaScript to stop a quantity field going below 1. Is that enough?

Idea 3: ordering fixes when a snippet has more than one flaw

When a snippet combines two issues, fix the one that gives the most direct control first (usually injection into a command or query), then the next. Applying fixes in isolation without checking they still work together can reopen a gap, so re-read the whole snippet once both fixes are in place.

Idea 4: defence in depth still matters

None of this replaces the layers from earlier rooms: least privilege, HttpOnly cookies, a Content Security Policy, quiet error pages, logging and monitoring. They don’t fix the flaw, but they shrink the damage if a fix is ever missed, and they are part of a mature secure coding practice.

Demonstration

Worked example. A fictional snippet from fernhill-market.example builds a query like this:

query = "SELECT * FROM products WHERE name LIKE '%" + search + "%'"
run(query)

A reviewer suggests two possible fixes:

Fix A (symptom):  if "'" in search: search = search.replace("'", "")
Fix B (cause):    run("SELECT * FROM products WHERE name LIKE ?", ["%" + search + "%"])

Fix A only blocks the one character this attack happened to need; a payload using a different route around the filter, or no quote at all, could still work. Fix B separates the query from the data entirely, so no value the user supplies can ever change the structure of the query, whatever characters it contains. That’s the real fix, and it’s the one this room asks you to pick every time.

Reflection questions

Discussion points

It separates the SQL structure from the data completely: the database treats user and pass purely as values, never as part of the instruction, no matter what characters they contain.

Discussion points

There are many ways to run JavaScript without the literal word "script" appearing, such as event-handler attributes like onerror. A word blacklist only ever covers the specific patterns its author thought of.

Discussion points

Discussion points

Key takeaways

  • A cause fix removes the flaw; a symptom fix only blocks the specific attack already tried.
  • Parameterised queries, output encoding, and path or command safety follow the same principle: keep data as data.
  • Client-side checks are a convenience, never a security control. The server must repeat them.
  • A snippet can combine more than one flaw, and each needs its own fix.
  • Defence in depth (least privilege, quiet errors, logging) backs up real fixes; it doesn’t replace them.
