Client-side trust: storage and validation bypass

Anything that runs in the browser can be read and changed by the person using it. This room shows you how to inspect and edit what a page trusts on the client side, and why the server must never take its word for it.

Introduction

A web page runs code in the visitor’s own browser: JavaScript, form fields, local storage, cookies. All of it is fully visible and fully editable by whoever is using that browser, using nothing more than tools already built into every browser. If a site relies on something in that environment staying as the developer left it, it is trusting data it does not control.

Why does it matter?

Prices, discount codes, user roles, quantity limits and validation rules are sometimes implemented only on the client, because it is quick and makes the page feel responsive. None of that is enforcement. Anyone can open the browser’s developer tools, or simply edit the request being sent, and the server sees whatever they choose to send it.

Where does this happen in real life?

E-commerce checkouts that trust a client-supplied price, admin panels that only hide a button rather than checking permission server-side, and forms that enforce limits purely with JavaScript are all common, real examples of this mistake.

An analogy

Imagine a shop where the price tag is handwritten by the customer and the till just reads whatever is written on it. The till isn’t checking a price list; it’s trusting a label anyone could have changed. The fix isn’t a harder-to-edit label, it’s a till that looks the price up itself.

Stay legal

Only test systems you own or have explicit permission to test. Manipulating a real site’s checkout or storage without authorisation is a criminal offence under the Computer Misuse Act 1990, even if no payment is ever completed. The simulated inspector in this room never touches your browser’s real storage, cookies, or any real site.

Learning objectives

  • Explain why anything in the browser is visible and editable by the user.
  • Use a simulated inspector to read values from client-side storage.
  • Edit a hidden form field and a client-side-only limit, and see how a vulnerable server responds.
  • Identify which value a page should never have trusted the client with.
  • Explain what server-side validation needs to check instead.

Theory

Idea 1: the browser is the user’s machine, not the developer’s

Once a page is loaded, its HTML, CSS and JavaScript are sitting on the visitor’s computer. Built-in developer tools let anyone view and edit the page, inspect storage, and see and change the exact request about to be sent. None of this requires special skill or special software: it ships with every modern browser.

  1. HTML & JSFully readable. Any logic inside it can be read and reasoned about.
  2. Hidden fieldsInvisible on the page, but present and editable in the HTML.
  3. Storage & cookiesReadable and writable through developer tools.
  4. The requestWhatever is actually sent to the server can be rewritten before it goes.

Idea 2: storing authority on the client

Some values represent authority: what a user is allowed to do, or how much something costs. If one of those lives only in the browser — a hidden field, a storage value, a cookie — the user effectively holds the final say over it, because they can change it before the server ever sees it.

Mini quiz: where does authority belong?

A checkout page stores the current user’s discount percentage in a cookie the browser sends with every request. What’s the problem?

Idea 3: client-side validation is a convenience, not a control

JavaScript that stops a form submitting with an empty field, or a maxlength attribute, makes the page pleasant to use. It runs entirely in the browser, so it can always be skipped: by disabling JavaScript, by editing the page, or simply by sending the underlying request directly, which is exactly what a tool like the inspector in this room lets you do.

Mini quiz: what proves a value is safe?

A page disables the "Buy" button until quantity is at least 1. Does the disabled button prove the server will only ever receive a valid quantity?

Idea 4: what the server must do instead

The server should treat every incoming value as untrusted, however it arrived, and look up or recompute anything that represents authority: re-fetch the real price from the database, re-check the user’s real role from their session, and re-apply every limit server-side, regardless of what the client claimed.

Demonstration

Worked example on a fictional site, riverbank-merch.example. A tester opens the checkout page’s developer tools and finds this hidden field:

<input type="hidden" name="unit_price" value="24.99">

They edit the value in the inspector before submitting:

<input type="hidden" name="unit_price" value="0.01">

If the server simply trusts whatever unit_price arrives with the order instead of looking the real price up itself, the order goes through at the edited amount. The fix is not to hide the field better or encrypt it: it is to never send the price to the client as something to be trusted back. The server should look the price up from the product ID alone.

Reflection questions

Discussion points

The price tier was stored entirely client-side, meaning the page relies on the browser to say who it’s dealing with rather than confirming that from a source the server controls, such as the logged-in session.

Discussion points

A hidden input is only hidden visually: hidden = "not displayed on the page", not "inaccessible" or "protected". It is still full, editable HTML sitting in the page source and still gets sent with the form exactly like a visible field.

Discussion points

The server multiplied price by whatever quantity it received without checking it was a sensible, positive number. That check needed to happen server-side, regardless of whatever the page’s own input restrictions claimed to enforce.

Discussion points

It would make the value harder to read, but the user can still change it to a value they can’t read either, or the client-side code that encrypts it can be studied and reproduced. The real fix removes the need to trust the client with the price at all: look it up server-side from the product ID.

Discussion points

Examples: an admin-only delete button that’s merely hidden from normal users (fix: check the user’s role server-side on every request, not just whether the button is shown); a "free shipping over £50" rule applied in JavaScript (fix: recalculate shipping server-side from the real basket total).

Key takeaways

  • Everything in the browser, including hidden fields and client-side storage, is visible and editable by the user.
  • Client-side validation is a convenience for honest users, not a security control.
  • Authority (price, role, permissions) must be looked up or re-checked server-side, never trusted from the client.
  • Hiding or obfuscating a value is not the same as removing the need to trust it.
  • The fix is almost always the same: the server recomputes or re-verifies anything that matters, regardless of what arrived in the request.
