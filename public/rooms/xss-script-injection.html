Cross-site scripting: when the page runs your input

Injection isn’t only for databases. When a page writes your input back without encoding it, the browser can’t tell your words from its own instructions. This room is a complete simulation: nothing you type here is ever executed.

Introduction

A web page is built from HTML, and the browser treats some characters as special: < starts a tag, and inside a tag a <script> block or an event attribute like onerror can run JavaScript. If a site takes your input and writes it straight into the page without encoding those characters, the browser can’t tell your text from the page’s own code. This is cross-site scripting, or XSS.

Why does it matter?

A script running on someone else’s page runs with that page’s privileges: it can read cookies, submit forms as the victim, redirect them, or quietly change what they see. It is the browser-side twin of the SQL injection you met earlier: input became instruction.

Where does this happen in real life?

XSS consistently appears in the most commonly reported web vulnerabilities. Comment boxes, search bars, profile fields and URL parameters are classic entry points, especially on sites that were never reviewed for it.

An analogy

Imagine a noticeboard where anyone can pin a note, and the office reads every note aloud over the tannoy. A normal note gets read as text. A note that says “ALSO: unlock the stationery cupboard” gets read as an instruction too, because the reader can’t tell notice from command. Encoding is teaching the reader to always say “the note says” first.

Stay legal, and a safety note

Only test for XSS on systems you own or have written permission to test. Doing this on a real site without authorisation is a criminal offence under the Computer Misuse Act 1990. Nothing in this room executes real code: payloads are analysed as text by a simulator, never run, so you can experiment freely.

Theory

Idea 1: output, not input, is where the damage happens

The danger isn’t that a user typed <script>. It’s that the page later wrote that text into HTML without encoding it. Encoding turns the special characters into harmless text equivalents:

Input:    <script>alert(1)</script>
Unsafe:   <script>alert(1)</script>        ← browser runs it
Encoded:  &lt;script&gt;alert(1)&lt;/script&gt;  ← browser shows it as text

The same input, written to the same page, is dangerous or harmless depending entirely on whether the output was encoded for where it landed.

Idea 2: three kinds of XSS

Reflected

Your input comes straight back in the response, usually from a search box or a URL parameter. It only affects whoever is tricked into clicking a crafted link.

Stored

Your input is saved (a comment, a profile field) and served to every later visitor. One post can affect everyone who reads it.

DOM-based

No server involved: client-side JavaScript reads something like the URL and writes it into the page itself, usually with innerHTML.

Mini quiz: which kind?

A comment left on a public blog post contains a hidden payload. Every visitor who later reads that post is affected. What kind of XSS is this?

Idea 3: context changes everything

The same character needs different encoding depending on where it lands. Text inside a tag, an HTML attribute, and a block of JavaScript each have different special characters, so a single generic filter is never enough:

In HTML body:       <p>USER_INPUT</p>              encode < > &
In an attribute:    <img alt="USER_INPUT">         also encode " and '
Inside JavaScript:  var name = "USER_INPUT";        needs JS-string encoding, not HTML encoding

Idea 4: defence in depth

No single defence is perfect alone, so good sites layer several:

  • Output encoding for the context (HTML, attribute, JavaScript, URL) — the actual fix.
  • Safe APIs like textContent instead of innerHTML, so there is no HTML to misinterpret.
  • Content Security Policy (CSP), which can stop injected scripts from running even if one slips through.
  • HttpOnly cookies, so even a successful script can’t read the session cookie.

Demonstration

Worked example on a fictional site, lochview-guestbook.example. Its search box writes your query straight back onto the page:

Request:   /search?q=badges
Response:  <p>You searched for: badges</p>

A tester tries a payload instead of a normal search term:

Request:   /search?q=<img src=x onerror=alert(document.cookie)>
Response:  <p>You searched for: <img src=x onerror=alert(document.cookie)></p>

The browser tries to load an image from a URL that doesn’t exist, fails, and runs the onerror handler — which is JavaScript, supplied entirely by the attacker. A crafted link containing this query, sent to a victim who is logged in, would run with their session. The fix is a one-line change: encode q before writing it into the page.

Reflection questions

Discussion points

Characters are only dangerous in the context the browser is reading them in. Unencoded, a < is read as the start of a tag; encoded, it is read as the text character "<". The data didn’t change; the output handling did.

Discussion points

HTML event attributes like onerror, onload and onclick can contain JavaScript directly. The browser doesn’t require a <script> tag specifically; it just needs somewhere it recognises as code.

Discussion points

Reflected XSS needs the victim to click a specific crafted link and only fires once. Stored XSS runs automatically for every visitor who views the affected page, with no link or trick required each time.

Discussion points

Output encoding (or a working CSP) stops the script executing in the first place. HttpOnly cookies don’t stop the script running; they only stop a script that does run from reading the session cookie. Both matter, but they do different jobs.

Discussion points

Examples: a user’s display name shown on a profile page, a product review, an error message that echoes back a search term. The fix is the same everywhere: encode the output for the context it’s written into, rather than trying to filter the input.

Key takeaways

  • XSS happens when unencoded input is written into a page the browser can execute.
  • Reflected XSS hits one victim per link; stored XSS hits every later visitor.
  • The same character is safe or dangerous depending on context: HTML body, attribute, or JavaScript.
  • Context-aware output encoding is the actual fix; filtering specific words is not.
  • HttpOnly cookies and CSP add real layers of defence, but they back up encoding rather than replace it.
