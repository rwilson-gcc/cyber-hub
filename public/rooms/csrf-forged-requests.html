CSRF: requests you never meant to send

Browsers attach your cookies to every request automatically, even ones a completely different website triggered without your knowledge. This room shows how that habit can be turned against you, and the defences that stop it. Everything is simulated.

Introduction

When you log into a site, your browser usually keeps a cookie that proves who you are on every later request. That is convenient, but it has a side effect: the browser sends that cookie automatically with any request to that site, including one triggered by a page you never meant to interact with. Cross-Site Request Forgery, or CSRF, is an attack built entirely on that automatic behaviour.

Why does it matter?

If a site only checks "does this request have a valid session cookie?", it can’t tell a request the user actually meant to make from one a hostile page quietly triggered on their behalf. Being logged in proves who you are; it says nothing about whether you meant to send this particular request.

Where does this happen in real life?

Any action that changes something while relying only on a cookie for authentication is a potential target: changing an email address, transferring funds, deleting an account, changing a password. A single crafted link or an auto-submitting form on an unrelated site is often all it takes.

An analogy

Imagine your front door has a lock that opens automatically whenever it recognises your coat, even if someone else is wearing it and simply knocked on your behalf. The lock proves the coat is yours; it proves nothing about who is currently wearing it or whether you asked for the door to be opened.

Stay legal

Only test systems you own or have explicit permission to test. Forging requests against real accounts without authorisation is a criminal offence under the Computer Misuse Act 1990. This room is a full simulation: no real cookies, cross-site requests or accounts are involved.

Learning objectives

  • Explain why a cookie alone proves identity but not intent.
  • Tell a state-changing request apart from a harmless one.
  • Read a simple request and spot that nothing in it proves the user meant to send it.
  • Build or edit a forged request so a vulnerable server accepts it.
  • Explain what an anti-CSRF token, SameSite cookies, and an Origin check each add.

Theory

Idea 1: cookies travel automatically

Once logged in, your browser stores a session cookie and attaches it to every request sent to that site, from any page, any tab, any source, without asking you each time. A hostile page doesn’t need to steal your cookie: it just needs to get your browser to make a request, and the cookie comes along for free.

<img src="https://bank.example/transfer?to=attacker&amount=500">

If that one line sits on any page you happen to visit while logged into bank.example, your browser requests it, cookie included, with no click required.

Idea 2: which requests are worth forging?

A request that only reads data (viewing a page) is a low-value target: forging it just shows the attacker a page, not the victim. A request that changes something — a transfer, a password change, a deletion — is the real target, because it performs an action as the victim.

Idea 3: why a cookie alone isn’t proof of intent

A server checking only "is there a valid session cookie?" is really only checking "is someone logged in?" It has no way to know whether the logged-in user actually clicked a button on the real site, or whether their browser was quietly directed to make the request by a page on a different site entirely. Something extra is needed to prove the request was genuinely intended.

Idea 4: the real defences

DefenceWhat it does
Anti-CSRF tokenA random, unguessable value the real page includes in the request. A forging page on another site has no way to read or guess it, so the server rejects requests without a matching token.
SameSite cookiesTells the browser not to send the cookie at all on requests triggered from another site, which stops most forgery attempts before they even reach the server.
Origin / Referer checkThe server checks where the request claims to have come from and rejects anything not from its own site.

Demonstration

Worked example. A fictional forum, glenfield-forum.example, lets a logged-in member delete their account with this request, authenticated only by a cookie:

POST /account/delete HTTP/1.1
Host: glenfield-forum.example
Cookie: session=abc123...

An attacker hosts this on a completely unrelated page:

<form id="f" action="https://glenfield-forum.example/account/delete" method="POST"></form>
<script>document.getElementById('f').submit()</script>

Anyone logged into the forum who merely visits the attacker’s page has their account deleted, with no click, no warning, and nothing on the attacker’s page even mentioning the forum. The request looked completely legitimate to the server: it had a valid cookie. It just wasn’t something the user asked for.

Reflection questions

Discussion points

An unpredictable, server-issued value (an anti-CSRF token) proving the request came from a page the real site actually served, not merely that the browser making it happens to be logged in.

Discussion points

The server’s only check was for a valid session cookie, and the browser attached that cookie automatically regardless of where the request originated. The server had no way to tell the request apart from one made on its own site.

Discussion points

Likely answer: the anti-CSRF token (or SameSite cookies, or an Origin check, depending on what was tried). A session cookie proves identity; the working defence additionally proves the request itself was intended, which a cookie alone cannot do.

Discussion points

Each defence covers slightly different cases and can have edge cases or compatibility gaps (for example, SameSite behaviour varies with older browsers or certain link types). Layering them means a gap in one is still likely caught by another.

Discussion points

A GET request can be triggered just by loading a URL, such as in an image tag or a link, with no form or JavaScript needed at all. Using GET for anything that changes data makes forging it as simple as getting the victim’s browser to load one URL.

Key takeaways

  • Browsers attach cookies automatically to every request, regardless of which page triggered it.
  • A valid session cookie proves identity, not intent.
  • State-changing actions are the real CSRF targets; read-only requests are low value to forge.
  • Anti-CSRF tokens, SameSite cookies, and Origin checks each independently stop forged requests.
  • State-changing actions should never be implemented using GET.
