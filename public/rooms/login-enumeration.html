Login enumeration: when error messages talk too much

A login form says more than "yes" or "no." Learn to read what its error messages are accidentally telling you, and why weak passwords make that information dangerous.

Introduction

Username enumeration happens when a login form responds differently depending on whether a username exists, even though it shouldn't matter to you at all. Combine that with a weak or default password, and an attacker suddenly has a clear path into an account.

Why does it matter?

Knowing a username is real narrows an attacker's job from "guess a username and a password" down to just "guess a password." That's a huge head start, especially against accounts using common or default passwords.

Where does this happen in real life?

Credential stuffing attacks, where attackers try huge lists of leaked usernames and passwords against login forms, rely on exactly this weakness. Many real breaches trace back to an account with a guessable username and an equally guessable password.

An analogy

Imagine knocking on doors down a street. Most doors stay silent. One door's intercom says, "Wrong code, try again," instead of nothing at all. You've just learned someone lives there, without them ever opening the door. Now you know exactly where to spend your time.

Stay legal

Only test login forms you own or have explicit permission to test. Trying passwords against real accounts you don't own is illegal. This room is a complete simulation, with no real accounts involved.

Learning objectives

  • Explain what username enumeration is and why it's a risk.
  • Compare a safe, generic login error with a risky, specific one.
  • Use differing error messages to identify a valid username.
  • Explain why common or default passwords are dangerous once a username is known.
  • Combine enumeration and a weak password to reach a protected page.

Theory

Idea 1: generic messages protect you, specific ones don't

ScenarioRisky messageSafer message
Username doesn't exist"That username doesn't exist.""Invalid username or password."
Username exists, wrong password"Incorrect password.""Invalid username or password."

The safe version gives exactly the same message either way, so an attacker learns nothing from trying a username.

Mini quiz: spot the leak

A login form shows "Account not found" for a bad username and "Wrong password" for a bad password on a real account. What's happening here?

Idea 2: the enumeration-to-access path

  1. 1. Try usernamesNote which ones get a different message.
  2. 2. Confirm oneThat username is real.
  3. 3. Try passwordsTest common or likely passwords against it.
  4. 4. AccessA weak password gets them straight in.

Idea 3: weak passwords are the second half of the problem

Common weak passwords include things like password123, a word plus a year (Summer2026!), or a word plus a short number (welcome1). None of these need "cracking" in a technical sense; they just need guessing, often from a short, predictable list.

Demonstration

Worked example on a fictional site, mapleview-gym.example:

Trying username admin with any password returns: Incorrect password.

Trying username sjones with any password returns: Account not found.

That one word, "Incorrect" versus "not found," confirms admin is a real account. From there, trying a short list of common passwords against admin is a quick next step, and on a badly configured site, one of them might work.

The fix: always show the same generic message, and add rate limiting so repeated guesses get slowed down or locked out.

Reflection questions

Discussion points

It's a binary signal: real account or not. Attackers don't need much information to narrow their search, and one word is enough.

Discussion points

Usability and security sometimes pull in different directions. Here, the security benefit (hiding which accounts exist) generally outweighs a small amount of extra friction for honest users.

Discussion points

Defences work in layers. Even if a site hides which usernames are valid, a weak password is still guessable through other means, like leaked password lists.

Discussion points

Key takeaways

  • Different error messages for "no such user" and "wrong password" leak which accounts are real.
  • A generic message that never changes closes that leak.
  • Once a username is confirmed, a weak password is often the only thing left to guess.
  • Rate limiting and lockouts add a second layer of defence.
  • Small wordlists and a little patience are often all an attacker needs against a weak setup.
