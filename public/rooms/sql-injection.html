SQL injection: when input becomes instruction

A website asks a database questions on your behalf. This room shows what happens when the site pastes your words straight into the question, and why that lets you change the question itself. Everything here is a simulation: no real database is involved.

Introduction

Most websites keep their information in a database, and they talk to it using a language called SQL. When you search for a product or log in, the site writes a short SQL question, sends it to the database, and shows you the answer.

Why does it matter?

If the site builds that question by gluing your text into it, then your text can include SQL of its own. The database can't tell which words the developer wrote and which words you typed, so it follows all of them. That single mistake can expose accounts, customer records and anything else the database holds.

Where does this happen in real life?

SQL injection has been well understood for over twenty years, yet it still turns up in real breaches because one careless line of code is enough to cause it. It sits in the injection category of the most commonly reported web vulnerabilities.

An analogy

Imagine a form at a bank that says "Pay to the order of ______". A clerk reads out whatever you write. If you write "Alice. Also, empty the safe.", a careless clerk might treat the second sentence as an instruction rather than a name. SQL injection is the same mix-up between information and instructions.

Stay legal

Only test for SQL injection on systems you own or have written permission to test. Sending these inputs to a real site without authorisation is a criminal offence under the Computer Misuse Act 1990, even if you only meant to look. This room is a complete simulation.

Learning objectives

  • Explain how a site builds a SQL query from user input, and where that goes wrong.
  • Recognise the three building blocks of a basic injection: a closing quote, a comment and an always-true condition.
  • Use a verbose database error to learn about a site's query.
  • Use ORDER BY and UNION to find a query's column count and read a table the page never meant to show.
  • Describe the real fix: parameterised queries, alongside quieter errors and least privilege.

Theory

Idea 1: the site writes a question, and your text goes inside it

Here is what a vulnerable search page does with whatever you type. The part in yellow is you. Everything else was written by the developer.

SELECT name, price FROM products WHERE name LIKE '%bike%'

Typing bike gives the database a tidy question. The quote marks around your text tell the database "this part is just text". Everything depends on those quotes staying where the developer put them.

  1. 1. You typeWords into a search box or login form.
  2. 2. Site builds SQLIt pastes your words into a query string.
  3. 3. Database runs itIt follows every instruction it finds.
  4. 4. Results come backShown on the page, or as an error.

Idea 2: breaking out of the quotes

If you type your own quote mark, it closes the text early, and whatever comes next is read as SQL. Three small pieces cover most beginner attacks:

A quote: '

Ends the text early so you can write SQL after it. On its own it usually causes an error, which is itself a clue.

A comment: --

Tells the database to ignore the rest of the line, including the developer's own closing quote or password check.

A true condition: OR 1=1

Always true, so a WHERE filter matches every row instead of only the ones the developer intended.

-- login query the developer wrote:
SELECT username FROM staff WHERE username = 'admin'--' AND password = ''
-- everything after the dashes is ignored, so the password check never runs

Idea 3: counting columns and joining tables

A search query returns a fixed number of columns. ORDER BY 3 sorts by the third column, so it works if there are at least three and fails if there aren't. Trying 1, 2, 3, 4 reveals the exact count. Once you know it, UNION SELECT lets you glue the results of a completely different query onto the page's own results, as long as it has the same number of columns.

' ORDER BY 4--     → error means fewer than 4 columns
' UNION SELECT a, b, c FROM other_table--

Idea 4: the fix is to keep code and data apart

The proper defence is a parameterised query (also called a prepared statement). The developer sends the SQL and the user's text to the database separately, so the text can only ever be treated as text, however many quotes it contains. Hiding error messages, limiting what the database account can read, and hashing stored passwords all help, but none of them replaces this fix.

query = "SELECT name, price FROM products WHERE name LIKE ?"
run(query, ["%" + user_text + "%"])   -- the ? is filled in as data only

Demonstration

Worked example on a fictional site, glenmuir-garden-centre.example, a plant shop with a search box:

A normal search for fern builds this query and returns two plants:

SELECT name, price FROM plants WHERE name LIKE '%fern%'

A tester then types ' OR 1=1-- into the same box:

SELECT name, price FROM plants WHERE name LIKE '%' OR 1=1-- %'

The quote closed the text, OR 1=1 made the filter always true, and -- threw away the leftover %'. The page now lists every plant in the table, including ones that were marked as hidden. The tester didn't need a password, a tool or any special access, only a different way of typing into a box.

The fix on the garden centre's side is a one-line change to a parameterised query. The vulnerable line and the safe line look almost identical, which is exactly why this bug survives code reviews.

Reflection questions

Discussion points

The quote closes the text early, so the leftover characters are invalid SQL. The debug output then revealed the query's shape and the table name, which is exactly the groundwork an attacker needs for the next step.

Discussion points

Filters try to spot bad input, and attackers keep finding new ways to write it (different cases, comments, encodings). Real names like O'Brien also contain quotes. Parameterised queries avoid the whole guessing game by never mixing input into the SQL.

Discussion points

The SQL and the user's text are sent to the database separately, so the text is only ever treated as a value and can never be read as part of the instruction.

Discussion points

Verbose errors leak table names, query structure and software details. They belong in private logs for developers, with a plain "something went wrong" message shown to visitors. This links back to the information-leaking headers you found earlier.

Discussion points

Examples: a database account with far more access than the site needs (fix: least privilege), passwords stored in readable form (fix: salted hashing), no second factor on staff accounts (fix: MFA), and verbose errors (fix: log privately).

Key takeaways

  • SQL injection happens when user input is pasted into a query, so the database can't tell data from instructions.
  • A quote, a comment and an always-true condition are the building blocks of the simplest attacks.
  • Verbose errors and a visible column count help an attacker move from guessing to reading other tables.
  • Filtering bad words is fragile. Parameterised queries are the fix that actually removes the problem.
  • Least privilege, hashed passwords and quiet error pages limit the damage if something is missed.
