HTTP headers: what your browser isn't telling you

Every request and response carries a hidden envelope of metadata. Learn to read it, and you'll spot leaks and missing defences that the page itself never shows you.

Introduction

When your browser asks a website for a page, it doesn't just send the address. It sends a bundle of extra information called headers, and the server replies with a bundle of its own. Neither bundle shows up on screen, but both are easy to read if you know where to look.

Why does it matter?

Headers often say more than they should. A server might announce exactly which software version it's running, handing an attacker a shortcut to known weaknesses. Or a site might simply forget to set headers that protect visitors, leaving the door open to attacks like clickjacking.

Where does this happen in real life?

Security scanners check headers automatically, and so do attackers. Missing security headers are one of the most common, most avoidable findings in real penetration test reports.

An analogy

Think of a parcel. The contents are the webpage. The label on the outside is the headers: sender, courier, handling instructions, maybe a barcode. You can learn a lot about a parcel without ever opening it, just by reading the label.

Stay legal

Only inspect headers on systems you own or have permission to test. This room is a complete simulation, so explore freely.

Learning objectives

  • Explain the difference between a request header and a response header.
  • Read an HTTP status code and know roughly what it means.
  • Recognise headers that leak information, such as Server and X-Powered-By.
  • Name common security headers and what each one defends against.
  • Find and decode a value hidden inside a response header.

Theory

Idea 1: a request and a response both carry headers

  1. 1. You askBrowser sends a request: method, path, and request headers.
  2. 2. Server repliesA status code, then response headers.
  3. 3. Then the bodyThe actual HTML, image or file.
  4. 4. You read itA header inspector shows all of this at once.

Idea 2: status codes are a quick summary

RangeMeaningExample
2xxSuccess200 OK
3xxRedirect301 Moved Permanently
4xxClient error403 Forbidden, 404 Not Found
5xxServer error500 Internal Server Error

A 403 on /admin confirms the page exists, it's just refusing you. That's useful recon, even without seeing the page.

Idea 3: some headers leak more than intended

Server: nginx/1.14.0
X-Powered-By: PHP/7.2.0

Naming the exact software version tells an attacker precisely which known weaknesses to try. Good practice is to remove or generalise these headers.

Idea 4: security headers are defences, not decoration

HeaderDefends against
X-Frame-Options / CSP frame-ancestorsClickjacking: the page being loaded inside an invisible frame on another site
Content-Security-PolicyLimits where scripts and content can load from, reducing XSS impact
Strict-Transport-SecurityForces the browser to always use HTTPS
X-Content-Type-Options: nosniffStops the browser guessing a file's type in a risky way

Demonstration

Worked example on a fictional site, northbank-shop.example:

GET / → 200 OK

Server: Apache/2.2.3
X-Powered-By: PHP/5.3.1
Content-Type: text/html

Apache 2.2.3 and PHP 5.3.1 are both very old. A quick search for either version turns up long lists of known weaknesses. The fix isn't to panic, it's to upgrade the software and stop announcing the exact version in headers.

GET /checkout → 200 OK

Content-Type: text/html
Set-Cookie: session=abc123

No X-Frame-Options or CSP here either. A page handling payments with no clickjacking defence is a real finding worth reporting.

Reflection questions

Discussion points

Version strings give attackers a head start on finding known weaknesses. Removing them doesn't fix the weaknesses, but it slows down casual scanning.

Discussion points

404 usually means nothing is there. 403 means something is there but protected, which tells you where to focus attention and what to report.

Discussion points

They're defence in depth: not needed for the site to function, but important when something else goes wrong, like a script injection or an embedded frame.

Discussion points

Both are public information nobody hid behind a login. Headers are metadata about the exchange, while source is the page's actual content and structure.

Discussion points

There's no single right answer. Many practitioners would start with removing version-revealing headers and adding a frame-protection header, since both are quick, free and low-risk changes.

Key takeaways

  • Headers are metadata that travel with every request and response, invisible on the page but easy to inspect.
  • Status codes give fast, useful signals, even for pages you can't open.
  • Headers like Server and X-Powered-By can leak exact software versions.
  • Security headers are free, simple defences that are easy to forget.
  • A header can hide an encoded value, just like a page's HTML can.
