Command and path injection: talking to the server’s system

Some pages don’t just query a database, they run a system command or open a file on the server’s behalf. When your input reaches that command or path unchecked, you can redirect what the server does, or read files you were never meant to see. Everything here is simulated.

Introduction

Some features need the server to do more than query a database: a network diagnostics page might run ping, or a document viewer might open a file by name. If the page builds that system command or file path by gluing in your text, the operating system can’t tell your data from the developer’s instruction, just like the database couldn’t in SQL injection.

Why does it matter?

A command injection can let an attacker run arbitrary commands with the web server’s own privileges: read files, install tools, or pivot further into the network. A path traversal can expose configuration files, credentials, or source code never meant to be public, using nothing more exotic than ../.

Where does this happen in real life?

Diagnostic tools (ping, traceroute, DNS lookups), image or document processing that shells out to another program, and file download or preview features that take a filename from the user are the classic places both flaws turn up.

An analogy

Command injection is like asking a courier to “deliver to 14 Mill Street, and also empty my bank account” and the courier, unable to tell instruction from address, tries to do both. Path traversal is like a filing clerk who, told to fetch “../../personnel/salaries”, walks straight out of the folder they were handed and into one they shouldn’t have access to.

Stay legal

Only test systems you own or have explicit permission to test. Running commands or reading files on a system without authorisation is a criminal offence under the Computer Misuse Act 1990. This room runs entirely inside a simulated command set and a fake file tree in your browser: nothing here executes on a real system.

Learning objectives

  • Explain how user input can end up inside a system command or a file path.
  • Recognise shell metacharacters that chain or redirect a command.
  • Use path traversal to escape a folder the server meant to confine you to.
  • Tell a blacklist-based fix apart from an allow-list-based fix, and say which is safer.
  • Explain why avoiding the shell entirely beats trying to sanitise input for it.

Theory

Idea 1: building a command from user input

A vulnerable diagnostic page might build a command like this:

cmd = "ping -c 1 " + user_input
run_in_shell(cmd)

Typed normally, user_input is just a hostname. But the shell treats certain characters specially, and those characters let one line of input become two commands.

  1. ;Ends one command, starts the next, regardless of whether the first succeeded.
  2. &&Runs the next command only if the first succeeded.
  3. |Pipes the output of one command into another.
  4. $( )or backticks run a command and substitute its output inline.
Mini quiz: chaining commands

A vulnerable page runs ping -c 1 USER_INPUT in a shell. Which input would most likely run a second, unrelated command afterwards?

Idea 2: walking out of a folder

A file-serving feature often takes a filename and joins it onto a base folder:

path = "/var/www/docs/" + filename
open(path)

If filename is allowed to contain ../, each occurrence moves one folder up before the rest of the path is applied. Enough of them walk straight out of docs/ and into any other folder the web server account can read.

filename = "../../etc/passwd"
path     = "/var/www/docs/../../etc/passwd"   →   "/etc/passwd"

Idea 3: why blacklists fail here too

A common but weak fix is to strip out dangerous-looking characters like ; or the string ../. Both are easy to bypass: a semicolon can often be swapped for a newline or &&, and ....// can collapse back into ../ once a naive filter removes the inner copy. Blacklisting specific bad patterns is always a step behind attackers who find a new one.

Idea 4: the real fixes

FlawWeak fixReal fix
Command injectionStrip semicolons and pipesNever build a shell string; call the underlying function directly with arguments, or use a safe library API
Path traversalStrip ../Resolve the final path and check it is still inside the allowed folder; use an allow-list of known filenames

Both real fixes share an idea from earlier rooms: keep user input as data, never let it become part of an instruction, whether that instruction is SQL, HTML or a shell command.

Demonstration

Worked example on a fictional site, harbour-netops.example, which has a "ping a host" diagnostic page. A normal request:

Input:    8.8.8.8
Command run on the server:  ping -c 1 8.8.8.8
Output:   PING 8.8.8.8: 1 packets transmitted, 1 received

A tester tries chaining a second command:

Input:    8.8.8.8; whoami
Command run on the server:  ping -c 1 8.8.8.8; whoami
Output:   PING 8.8.8.8: 1 packets transmitted, 1 received
          www-data

The semicolon ended the ping command and started a brand new one, which ran with the web server’s own account. From here, an attacker could try to read files, look for credentials, or explore the network — all without ever touching a login page.

Reflection questions

Discussion points

It built a single text string by gluing user input onto a fixed command and handed the whole thing to the shell. The shell interprets its own metacharacters wherever it finds them, with no way to know which part the developer wrote and which part came from a user.

Discussion points

Each ../ in the filename moved the resolved path up one folder before the final filename was applied, walking it out of docs/ entirely. The server simply joined the user’s text onto a base path without checking where the result actually ended up.

Discussion points

A strip-based filter only blocks the specific patterns its author thought of. Attackers can often find alternative encodings, double the pattern so a single removal pass leaves one copy behind, or use a different separator the filter didn’t consider. Avoiding the shell, or checking the real resolved path, removes the whole class of bypass.

Discussion points

Even a low-privilege account can usually read some files, see environment variables, make outbound network connections, or act as a foothold for further attacks (privilege escalation, lateral movement). Least privilege limits the damage; it doesn’t eliminate it.

Discussion points

Examples: converting an uploaded file with an external tool (use a library with a proper API rather than shelling out), generating a PDF report by filename, running a backup script with a user-supplied name. Safer design: call the underlying library function directly with arguments, never a shell string, and validate any filename against an allow-list or a generated, non-guessable name.

Key takeaways

  • Building a shell command or file path from user input lets that input become an instruction.
  • Shell metacharacters like ; && | chain or redirect commands.
  • ../ walks a file path up and out of the folder it was meant to stay in.
  • Blacklisting specific dangerous characters or strings is fragile and usually bypassable.
  • The real fix is avoiding the shell entirely, or validating the resolved path and filename against what is actually allowed.
